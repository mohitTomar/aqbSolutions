# AUDIT.md

# FinTrack Pro — Code Audit

| # | File | Location | Severity | Category | Description | Correct Fix |
|---|------|----------|----------|----------|-------------|-------------|
| 1 | `app/api/v1/reconcile/route.ts` | POST — raw SQL insert | Critical | Security | SQL injection vulnerability via string interpolation in `INSERT INTO reconciliation_runs` query using untrusted `notes` input. | Use parameterized Drizzle ORM query or prepared statements instead of string interpolation. |
| 2 | `app/api/v1/reconcile/route.ts` | GET — raw SQL select | Critical | Security | SQL injection vulnerability via `id` query parameter in `SELECT * FROM reconciliation_runs WHERE id = '${id}'`. | Use ORM query builder or parameterized query validation. |
| 3 | `app/api/v1/reconcile/route.ts` | Entire route | Critical | Security | No authentication or authorization on reconciliation endpoints. Any caller can trigger or fetch reconciliation runs. | Enforce authenticated session using `getSession()` and return `401 Unauthorized` for unauthenticated requests. |
| 4 | `app/api/v1/reconcile/route.ts` | Catch block | Critical | Compliance | Internal stack traces are returned to API consumers via `error.stack`. This leaks implementation details and may expose sensitive infrastructure information. | Log internally and return sanitized generic error messages to clients. |
| 5 | `lib/services/reconciliation/reconciler.ts` | `findMatch()` | High | Logic | Matching strategy uses amount-only comparison. Multiple payments may share the same amount, causing incorrect reconciliation results. | Use deterministic matching strategy based on external reference, currency, amount, and date tolerance. |
| 6 | `lib/services/reconciliation/reconciler.ts` | Monetary calculations | Critical | Logic | Monetary arithmetic uses JavaScript floating-point numbers for financial calculations, risking precision errors. | Use integer cents or decimal-safe monetary representation internally. |
| 7 | `lib/services/reconciliation/reconciler.ts` | `markReconciled()` | High | Logic | Payment status is only updated if status is `pending`. Payments in `cleared` state will never become reconciled. | Allow reconciliation from valid transitional states such as `pending` and `cleared`. |
| 8 | `lib/services/reconciliation/reconciler.ts` | `markReconciled()` | High | Performance | N+1 query pattern: each matched payment triggers an additional select and update query. | Perform reconciliation updates in a single transactional batch operation. |
| 9 | `lib/services/reconciliation/reconciler.ts` | Entire reconciliation flow | Critical | Logic | No transaction or locking mechanism. Concurrent reconciliation requests can reconcile the same payment multiple times. | Use database transaction with row-level locking or optimistic concurrency protection. |
| 10 | `lib/services/reconciliation/reconciler.ts` | `parseBankDate()` | High | Logic | Bank dates are parsed without timezone normalization or validation. Ambiguous timestamps may reconcile into incorrect periods. | Validate and normalize timestamps to UTC before comparison. |
| 11 | `lib/services/reconciliation/reconciler.ts` | `isInPeriod()` | Medium | Logic | Period filtering logic uses exclusive end boundary but database query uses `between()`, which is inclusive in many SQL implementations. This creates inconsistent reconciliation behavior. | Use explicit `gte` + `lt` conditions consistently across application and database filtering. |
| 12 | `lib/services/reconciliation/reconciler.ts` | Discrepancy handling | High | Logic | `discrepancies` array is never populated even when mismatches exist. | Implement discrepancy detection for amount mismatch, ambiguous matches, duplicate references, and unsupported currencies. |
| 13 | `lib/services/reconciliation/reconciler.ts` | `bankOnly` calculation | Medium | Logic | Unmatched bank records include records outside the reconciliation period because filtering uses the original `bankData` array. | Calculate unmatched records only from period-filtered bank records. |
| 14 | `lib/services/reconciliation/reconciler.ts` | Summary totals | Medium | Logic | `totalBankAmount` includes all uploaded records even if outside reconciliation period. | Calculate totals only from period-qualified records. |
| 15 | `lib/services/reconciliation/reconciler.ts` | Currency handling | High | Logic | No currency validation despite stated USD-only scope. Non-USD records may reconcile incorrectly. | Explicitly validate and reject or flag unsupported currencies. |
| 16 | `lib/services/reconciliation/reconciler.ts` | Duplicate bank transactions | High | Logic | Duplicate `transactionId` values are not detected, allowing duplicate reconciliation. | Validate uniqueness of bank transaction IDs within the uploaded batch. |
| 17 | `lib/services/reconciliation/reconciler.ts` | Payment reuse prevention | Medium | Logic | A payment can potentially be matched incorrectly if duplicate or ambiguous candidates exist. | Implement deterministic single-match constraints and ambiguity detection. |
| 18 | `lib/services/reconciliation/reconciler.ts` | Persistence logic | Medium | Compliance | Reconciliation persistence stores only aggregate counts without detailed audit linkage between bank records and payments. | Persist reconciliation mappings and discrepancies for auditability. |
| 19 | `lib/services/reconciliation/reconciler.ts` | Status persistence | Medium | Logic | Reconciliation run is always saved with status `complete` even if discrepancies or failures occur. | Use lifecycle statuses such as `running`, `complete`, `failed`, and `requires_review`. |
| 20 | `app/api/v1/reconcile/route.ts` | POST validation | Medium | API | Zod schema accepts arbitrary currency strings and does not constrain supported currencies. | Restrict currencies explicitly (e.g. `USD`) or validate against supported enum. |
| 21 | `app/api/v1/reconcile/route.ts` | GET endpoint | Medium | API | GET endpoint does not validate missing or malformed `id` parameter. | Return `400 Bad Request` when `id` is absent or invalid. |
| 22 | `app/api/v1/reconcile/route.ts` | GET endpoint response | Medium | API | GET endpoint returns raw database result instead of stable API contract expected by dashboard. | Return structured JSON response with typed `runs` payload. |
| 23 | `components/reconciliation/ReconciliationDashboard.tsx` | `useEffect()` | Medium | Performance | `setInterval()` is never cleaned up, causing memory leaks and duplicate polling on remounts. | Return cleanup function calling `clearInterval(interval)`. |
| 24 | `components/reconciliation/ReconciliationDashboard.tsx` | Data loading | Medium | Logic | Dashboard fetches `/api/v1/reconcile` without `id`, but backend GET handler expects an `id` parameter. Dashboard can never load correctly. | Align API contract to support list retrieval or update dashboard request accordingly. |
| 25 | `components/reconciliation/ReconciliationDashboard.tsx` | Error handling | Low | API | Errors during polling are silently ignored, making operational troubleshooting difficult. | Add controlled logging and user-visible error state. |
| 26 | `components/reconciliation/ReconciliationDashboard.tsx` | Polling strategy | Medium | Performance | Continuous polling every 3 seconds without visibility checks or backoff increases unnecessary load. | Pause polling when tab is hidden or use adaptive refresh strategy. |
| 27 | `components/reconciliation/ReconciliationDashboard.tsx` | Date rendering | Low | UX | Raw ISO date strings are rendered directly without formatting, reducing readability. | Format dates using locale-aware formatter. |
| 28 | `components/reconciliation/ReconciliationDashboard.tsx` | Accessibility | Low | Compliance | Status badges and interactive controls lack accessibility metadata/tooltips. | Add accessible labels and semantic attributes. |
| 29 | `lib/services/reconciliation/reconciler.ts` | Matching algorithm scalability | Medium | Performance | For every bank record, remaining payments are filtered repeatedly, creating O(n²) behavior. | Pre-index payments using maps keyed by reference/amount for efficient lookup. |
| 30 | `lib/services/reconciliation/reconciler.ts` | Validation | Medium | Logic | No validation exists for negative amounts, invalid dates, or malformed references. | Add input validation before reconciliation processing. |
| 31 | `app/api/v1/reconcile/route.ts` | HTTP semantics | Medium | API | All failures return HTTP 500 regardless of validation or auth failures. | Return correct status codes such as 400, 401, 403, 404, and 500. |
| 32 | `lib/services/reconciliation/reconciler.ts` | Auditability | Medium | Compliance | No operator/user attribution is stored with reconciliation runs. | Persist authenticated user ID for audit trail compliance. |
| 33 | `lib/services/reconciliation/reconciler.ts` | Idempotency | High | Logic | Re-running reconciliation for the same period may create duplicate reconciliation records and inconsistent state. | Add idempotency strategy or uniqueness constraints for reconciliation runs. |
| 34 | `app/api/v1/reconcile/route.ts` | Request size protection | Medium | Security | No request size or batch-size validation exists. Large uploads could exhaust memory or degrade service. | Add payload size and batch count limits. |
| 35 | `lib/services/reconciliation/reconciler.ts` | Date comparison | Medium | Logic | `new Date()` parsing behavior depends on runtime/environment for malformed or timezone-less values. | Use strict ISO validation and explicit UTC parsing strategy. |
